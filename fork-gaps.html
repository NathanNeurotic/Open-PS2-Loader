Fork Feature Gaps

Features, fixes and companion workflows that other PS2 loaders, forks and utilities offer beyond RiptOPL and the PS2-Servers ecosystem. Each entry was checked against RiptOPL's own code rather than taken from another project's changelog, and links to where that project implements it.

A tracking list, not a roadmap
An entry documents a source-specific capability absent from RiptOPL or its PS2-Servers companion, with optional design choices and experimental features separately labelled. An entry does not promise a port. Source comparisons refreshed on 2026-10-08 UTC (2026-10-07 Pacific); RA merge reconciled on 2026-10-08 Pacific against rebuild/main@9ef8d643. This pass rechecks changed OPHTML, LUNA, xeRAbora/OPL-RA and PS2-Launcher sources, verifies the surveyed repositories' current revisions, and reconciles already implemented RiptOPL features. Existing historical rows retain their original evidence unless explicitly updated. See revision and validation scope and retired IDs. Stable IDs are never reassigned. Tools and developer APIs are distinguished from game-loading features; source, emulator and console evidence are separate.

What did not become a gap: The console launcher & runtime overlap
OPHTML also contains a standalone console game launcher (console/ophtml.elf) and sample environments (opl-env, channel6), its core game-loading and management capabilities directly overlap existing RiptOPL infrastructure and are not counted as gaps:
  • Neutrino No-IOP-Reset launch handoff: OPHTML launches Neutrino using -qb, -bsd=, and -dvd= through LoadELFFromFileWithPartitionNoReset. RiptOPL already has full native No-IOP-Reset handoff (src/elfldr_noreset.c), copying the child loader into BIOS-unused memory at 0x84000 and passing target paths and arguments to ExecPS2 so Neutrino can read its config and ISO without resetting OPL's live storage mounts.
  • In-memory ISO9660 volume & SYSTEM.CNF title ID extraction: OPHTML traverses sector 16 PVD records and parses SYSTEM.CNF in memory. RiptOPL already performs sector 16 PVD root-directory traversal in memory to extract BOOT2 game IDs and creation timestamps (src/retrogem.c and src/ps2cnf.c).
  • Dynamic cover art streaming & VRAM texture caching: OPHTML's streaming texture slots overlap RiptOPL's dedicated async texture worker (src/texcache.c), which provides lookahead caching, multi-epoch invalidation, chunked staging, memory clamps, and SIO2 controller-bus read throttling.
  • Virtualized list windowing & selection binding: OPHTML's ps2ui_list windowing and selection clamping are standard OPL core features in RiptOPL's item and GUI management.
  • Multi-device & SD2PSX/MMCE support: USB, internal HDD, MX4SIO, and MMCE channel support are already implemented in RiptOPL's storage drivers and RetroGEM/SD2PSX integration.
Validation status and emulator testing
OPHTML v0.10.0's ophtml.elf launcher has booted and proven its D-pad navigation and list virtualisation inside the Play! emulator in CI (via automated pad input injection and frame diffing). However, because Play! does not emulate USB, HDD or memory card controllers, physical-console bench cases C1–C8 remain formally [open] pending physical-console reports. Conversely, its underlying ps2ui GS rasterization runtime has undergone extensive physical PS2 hardware validation across multiple test sessions (documented in docs/bench-phase1.md and docs/bench-phase2.md).

The new OPL compatibility resolver maps only verified modes 2, 3 and 5; GSM and VMC CFG mapping remain unfinished. Last-played restoration overlaps RiptOPL. The launch breadcrumb records an attempted handoff but is not a proven hang detector or retry UI; it is not counted as one.

Compatibility and implementation boundaries

Do not assume the two ecosystems can be swapped by changing the server address. Caduceus OPL expects the paired PS2 SMB share (normally port 1024), plus custom RA catalogue/session and account APIs on UDP 18197/18198. PS2-Servers Desktop normally advertises SMBv1 share games on port 1025 (Core/Edge default to 1111). Share name, port, root layout, credentials, services and console configuration must match. Two services cannot both bind the same host address, protocol and port. Caduceus' custom achievement browser needs a compatible server component; serving the same ISO files via PS2-Servers does not supply it.

Both ecosystems inherit the upstream warning that RA telemetry during SMB game streaming can disrupt loads; neither pairing demonstrates a fix for that issue. Keep host tokens and the Caduceus read-capability key private; UDP catalogue traffic is not encrypted. Caduceus PC sources currently have no top-level declared GitHub repository licence, so obtain clear reuse permission or review licensing before copying original application/bridge code. The inherited OPL/xeRAbora components have their own licences and notices.

Integration priorities for our pairing

  1. Optional PC library module: add metadata/catalogue, cover preparation, installed-game inventory and non-destructive backup as a frontend/sidecar to PS2-Servers; keep existing service implementations unchanged. Account for RiptOPL's disc-ID PS2 art and filename/folder-based VCD, ELF and Ember art identities.
  2. Read-only game-session reporting: surface the running title and its image/cover to an optional desktop view; only add Discord presence if the session identity is dependable. Avoid injecting traffic or polling into the hot UDPFS/SMB transfer paths.
  3. Optional RA account viewer: build on the compatible xeRAbora client already used by RiptOPL, with secrets held on the host, bounded requests and a separately tested console-side browser. Do not introduce a competing telemetry client or incompatible protocol by default; treat OR4 as the single existing console gap.
  4. Integration tests first: verify share/port selection, art naming, concurrent listeners, offline fallback, IOP resets, real-PS2 UI memory limits and performance before treating the pairing as interchangeable. Preserve existing servers and saved libraries during any migration.
